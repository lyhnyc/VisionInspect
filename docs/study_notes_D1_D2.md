## 第二部分：Git / GitHub 完全入门（没用过的人从这里读）

### Git 和 GitHub 分别是什么

- **Git**：装在你电脑里的"版本记录仪"。它把你项目里每个文件的每次修改都记成"快照"（commit），随时能回看、能回退、能对比。
- **GitHub**：放快照的网站（github.com）。把本地快照推上去，等于：①云端备份 ②别人能看到你的代码历史（面试官看的就是这个）。

### 仓库里的各种东西，各是什么

**VisionInspect 文件夹（仓库）里的文件：**

| 文件/文件夹 | 是什么 | 为什么存在 |
|---|---|---|
| visioncore/ | C++ 核心算法工程 | JD 的图像算法在這里写（缺陷检测、卡尺测量） |
| visionapp/ | C# 上位机工程 | JD 的"界面开发"，WPF 界面在这里 |
| docs/ | 文档（SRS 需求、devlog 开发日志、recap 总结） | JD 的"文档编写"项，也是面试素材库 |
| tests/ | 单元测试代码（gtest） | JD 的"单元测试"要求 |
| CMakeLists.txt | CMake 构建说明书 | 告诉编译器"怎么把几十个 cpp 编译成一个程序" |
| .github/workflows/ci.yml | 持续集成配置 | JD 的"持续集成"：每次 push，GitHub 自动帮你编译+跑测试，防止坏代码进主干 |
| .gitignore | 排除清单 | 声明哪些文件不进版本库（如 build 中间产物），否则仓库会塞满垃圾 |
| tools/gen_defects.py | 造数据脚本 | 生成 201 张合成缺陷图当测试数据 |

### git 命令逐个解释（你敲过的每一条）

```
git init                          在当前文件夹"初始化"一个仓库（装上版本记录仪）
git config --global user.name     告诉 git 你是谁（写进每笔快照的署名）
git config --global user.email    同上，邮箱是 GitHub 识别你账号的依据
git status                        看"现在有什么改动没存档"（?? = 新文件没存过，M = 改过没存档）
git status -sb                    精简版；ahead 1 = 本地比 GitHub 多一笔（没推）
git add 文件名                    把文件"装箱"：决定这一笔快照包含哪些改动
git add .                         装箱全部改动
git commit -m "说明"              "拍快照"：把装进箱的改动永久记录进历史，-m 后是你写的说明
git log --oneline                 查看历史快照列表（每笔一行）
git push                          把本地快照上传到 GitHub（要联网）
git pull                          反向：把 GitHub 上别人的更新拉下来
```

**三段式心法**：`add`（装箱）→ `commit`（快照存档，只在本地）→ `push`（上云）。每天循环用，14 天后形成肌肉记忆。

### 你踩过的 5 个坑（面试叙事库，每条都是 JD 的"现场调试能力"证据）

**坑 1：OpenCV 安装包双击没反应**
现象：174MB 官方 exe，静默参数全失效。
根因：分段下载断流导致文件损坏（文件头是好的，内容烂了）。
教训：**下载大文件必须校验完整性**，不能只看"能不能双击"。

**坑 2：MSVC 编译错但代码没错**
现象：满屏 C2001/C2143，代码肉眼看没毛病。
根因：源文件是 UTF-8 无 BOM，MSVC 默认按 GBK 解码，中文注释的字节被误读吞掉了引号。
教训：**Windows 工具链默认编码不是 UTF-8**，跨平台源码要显式声明编码。

**坑 3：亚像素测量在旋转场景恒差 1px**
现象：水平方向误差 <0.1px，转 30° 后稳定差 1.03px。
根因：用 Python 复现算法发现算法本身无偏（-0.05px），问题出在**测试图**的 fillPoly 锯齿。
教训：**测试红了先怀疑测试本身**。

**坑 4：CMake 找不到 VS**
现象：cmake -G "Visual Studio 17 2022" 报找不到实例。
根因：LTSC 17.8 没注册进 VS Installer 元数据。
教训：**生成器只是查找器，真正干活的是 cl.exe**，可以手动喂环境变量绕过。

**坑 5：C# 里写 C 的 long long**
现象：P/Invoke 声明照抄 C 头文件编译失败。
根因：C 的 long long 不是 C# 类型，且 Windows 的 long 是 32 位。
教训：**跨语言边界类型必须按平台 ABI 精确匹配**。

## 第五部分：你这两天学到的（课程部分）

### 第 1 课：SSD 滑窗（lesson3_1.py，14 行）

**知识点**：模板匹配的本质 = 一维滑窗打分。

**你已经掌握的**：
- 滑窗：从信号上逐位置切出与模板等长的窗口
- SSD 打分：相减→平方→求和；完美匹配=0
- argmin：分数表里最小值的下标=匹配位置
- 长度不一致不能直接减：**切片保证相减双方永远等长**（你问过的问题，答案就在 window=sig[i:i+3] 这行）
- 函数名是标签：def 定义、调用处名字对上就行；SSD=Sum of Squared Differences 差的平方和

### 第 2 课：二维图像滑窗（lesson3_2.py，20 行）

**知识点**：一维滑窗 → 二维图像，本质没变只是下标多一维。

**你已经掌握的**：
- numpy 图像 = 二维数组，img[行, 列]，先行后列
- 切片含头不含尾：img[50:60] 实际是 50~59
- .copy() 的必要性：不加是"视图"，改一个动两个（numpy 经典暗坑）
- 二维滑窗：双重循环 y/x，result 尺寸 = image − template + 1
- 手写版 = OpenCV：cv2.matchTemplate + TM_SQDIFF 就是你写的双重循环
- 坐标坑：numpy (行,列) vs OpenCV (x,y)=(列,行)，顺序相反
- 边缘遮挡：残块（被裁掉一半的目标）会把窗口挤到地图边缘，SSD 不为 0 → 工程上要配分数门限

### 浮点误差与容差（昨天最后的大招）

你已经亲眼验证：完美匹配的 SSD 数学上=0，但 OpenCV 算出 3.05e-05，原因是它内部用代数变形 ΣI²−2ΣIT+ΣT²（大数相减），float32 在 100 附近的最小刻度是 7.63e-06，残渣恰好 4 个刻度。灰度翻倍残渣翻 4 倍（∝灰度²）。

**工程结论**：数字世界没有精确的 0，只有"误差<容差算过"。所以 C++ 代码里写 `if (std::fabs(denom) < 1e-6f)`、亚像素断言写 `误差<0.1px`。面试金句：能讲出"OpenCV SQDIFF 在 float32 下有 ULP 级残渣、随灰度平方增长，所以判级必须用容差"——直接甩开只会调库的人。

### 昨天 3 个输出逐个解读（你贴过的）

1. `res.shape = (51,51)`：60−10+1=51，打分地图尺寸=图−模板+1
2. `res[50,50] = 3.05e-05`：贴墙白块的完美匹配分数，"约等于 0"≈0
3. `res[51,51] → IndexError`：数组下标 0~50，第 51 个格子的下标是 50——越界当场报错（C++ 里这种错是段错误，更凶险）
